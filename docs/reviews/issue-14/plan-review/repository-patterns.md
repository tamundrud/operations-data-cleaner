## Repository Research Summary

### Implementation Patterns

The requested scope is an internal React/worker/session change with no external API or persisted workflow-schema change needed. The one-source-row-to-one-output-row engine, immutable original source table and worker-owned full `Run` should stay authoritative.

1. **Presentation causes need engine provenance.** `src/engine/issues.ts` currently has only one optional `source` and no causal relationship, operand role, rule identity or affected fields. `src/engine/recipes.ts` defaults `source` only for copy/split, so a calculation catch cannot identify either operand. `src/engine/decimal.ts` parses left then right and raises generic `NumericError`, losing which input failed and concealing a simultaneously invalid right input. Preserve full raw issue emission/summary semantics, but enrich causes where produced and project actionable review items separately. Avoid grouping by message. A split cause identity must include row, source, delimiter, expected segments and relevant empty-segment policy; segment output index must not prevent four outputs sharing a single count failure. Distinct policies/source cells/rules must stay distinct. Required-blank suppression must link to actual upstream failure for the same output, not merely any error on a row.

2. **Independent source inspection requires protocol changes.** `src/processing.worker.ts` currently slices `sourceRows` from the selected output-preview rows in `view(page, exceptions, invalidOnly)`, so source and output filters/pages are literally the same selection. It keeps the entire immutable source table, full run, ID index and full exception rows in worker memory, so separate source filter/page/target requests can reuse those authoritative collections. Extend `src/session/worker-protocol.ts` View with source selection metadata and per-source-row diagnostics rather than transmitting all records. The inspector must work with workflow-level errors too: current code falls back only to source first 50 rows when `run.workflowIssues.length` is nonzero.

3. **Preserve identity, never derive targets from visible positions.** `SourceRow` (`src/engine/values.ts`) has stable ID, original record/line and optional worksheet; `ResultRow` mirrors ID/record/line. Source navigation should resolve the stable ID against the full worker collection, choose source page independently, return focused target information, and open/focus the inspector only for explicit issue navigation. Existing `SourceCorrection` already displays current value, `original` and `ExcelCellDetails`, including formatting/formula/date provenance. Preserve that view for all staged/applied/reverted cases.

4. **Commit batch state only after successful worker acceptance.** `Session.correct` currently mutates its recovery `corrections` array before sending a single-cell request; worker currently mutates its own overlay before reevaluation. Both patterns need a candidate overlay for atomic batch failure safety. Validate every row/column and revision before any mutation, calculate once against a candidate overlay, then commit candidate overlay/run/revision together. Session should retain committed overlay separately from staged edits and promote the candidate only on matching accepted view. Cancellation/crash/retry must replay committed overlay only and retain pending intent where feasible; an unsuccessful or cancelled replacement currently preserves active original file and applied overlay through `Session.candidate` semantics.

5. **Stage above cell components.** `src/ui/SourceCorrection.tsx` owns local edit/value state and an Apply correction form; cells unmount when source disclosure closes or pagination changes. Pending values must be Session- or Workspace-owned by dataset/row/column and rendered as controlled inputs; component-local state cannot preserve multi-page edits. Preserve empty-string edits as actual changes and make same-as-current edits remove staging. Preserve literal numeric/date correction interpretation, which already flows through `correctedRun` and replacement `SourceCell.original`.

6. **Keep navigation state across revalidation.** Worker currently returns page zero with no exception filters after every non-page action. Batch apply must retain coherent source context, allow viewing just-resolved corrected rows, and offer next unresolved without forcing scroll. A remembered/recent corrected-ID subset or explicit corrected-row option can support confirmation while filtered membership legitimately changes. Output preview page/filter should be independent; clamping only when changed results require it is sufficient.

7. **Done editing needs a separate activation capability.** `src/ui/Workspace.tsx` uses `repeat` as the sole editor visibility flag; `Edit workflow` simply sets false with no inverse. Track whether current workflow came from saved/imported activation separately from display mode. Done editing should only toggle visibility, not call `saved`, `snapshot`, `activate`, `resetWorking` or `configure` directly. The `baseline` codec comparison already distinguishes unsaved config from `dirty` (pending validation) and must remain intact. Imported workflows may have no stored baseline, so saved-baseline presence alone is insufficient.

8. **Loss/export guards must cover all actual entry paths.** `Workspace.confirmReplacement`, new conversion, SavedWorkflows activation/import, source uploads, sample buttons, source delimiter changes, source disclosure closing and browser unload can lose or hide correction intent. Add explicit pending confirmation where loss occurs, preserve on cancel, and discard only after successful source replacement/activation. Download gating belongs in both Workspace `canExport` and `Session.export`; existing `Session.acknowledgePartial` and Workspace formula `choice` must reset when applicable results change. Do not couple read-only source pagination to partial-export permission revocation.

### Existing tests to extend

- `tests/unit/session.test.ts` uses a worker transport harness to prove request/dataset/revision rejection, recovery, cancelled delayed replacement, stale same-worker correction replies and export acknowledgement. Extend it with staging persistence, one batch request, rejected batch rollback, stale batch view, retry and export blocking.
- `tests/unit/corrections.test.ts` already proves immutable originals, corrected provenance, exact dependent calculation output, full candidate counts, missing trailing source cells, Excel metadata/date literals and incremental/full-run equivalence. Add multi-row/multi-cell atomic input and original/revert regressions.
- `tests/e2e/correction-reupload.spec.ts` tests exact downloaded bytes, no source persistence/leaks, 10,000 rows with later-page corrections, filtered targeting, direct production-worker stale requests, cancellation during replacement parsing, missing trailing fields and Excel typed correction. Its helper currently applies each cell immediately and its pagination assumptions must be intentionally updated to the new staged UX.
- `tests/e2e/helpers.ts` provides real upload, recipe configuration, preview and byte-download paths; reuse them for #14 scenarios instead of mocked UI responses.
- `tests/e2e/accessibility.spec.ts` uses Axe WCAG 2/2.1 AA and 1366/1024/390 widths. New pending/error/focus/action controls should receive equivalent coverage, including no page overflow.
